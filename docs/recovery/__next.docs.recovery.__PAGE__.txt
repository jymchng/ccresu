24:T3b2c,# How recovery works

> From the limit banner to a verified resume, through an explicit persisted state machine.

A recovery is a chain of recorded state transitions, not a fire-and-forget command. Each transition is validated against an edge table before it is written, so an impossible step is an error rather than a corrupted history.

The happy path:

```sh
DISCOVERED -> RUNNING -> USAGE_LIMIT_DETECTED -> WAITING_FOR_RESET
  -> RESET_TIME_REACHED -> CHECKING_SESSION -> CHECKING_LIMIT
  -> RESUMING -> RESUMED
```

## Off the happy path

| State | When it is recorded |
| --- | --- |
| RETRY_WAIT | An attempt failed and the budget still has room, or the pre-resume check failed and no attempt was spent; the loop returns to CHECKING_SESSION after a backoff. |
| DISCOVERED | The attempt budget is spent, or a resume attempt failed with an error classified as non-retryable. |
| COMPLETED | The session finished normally before the limit, so there is nothing to resume. |
| USER_TERMINATED | The user cancelled the session. |
| DISABLED | Recovery was switched off with `ccresu disable`. |
| UNRECOVERABLE | The session type or the observed error cannot be resumed with the documented CLI. |

**Figure: The chain, the retry loop and the two ways out**

The solid line is the recorded chain: discovery, the detected limit, the wait, the reset instant, the session check, the limit check and the resume. The dashed line is a failed attempt with budget left, which returns to the session check after a backoff. An attempt that fails with the budget spent, or with an error classed as non-retryable, ends in DISCOVERED; `ccresu retry <id>` is the only operator edge from there, and it lands in DISABLED.

(An SVG diagram on the page; it is not reproduced in text. See https://jymchng.github.io/ccresu/docs/.)

## What “resume” actually runs

ccresu uses five verified interfaces: discovery (`claude agents --json`), the session transcript and per-session environment directories under `~/.claude`, the resume command below, and `claude stop <job-id>` for one narrow case. Nothing else is invoked, and no new session is ever started in place of the original one.

The resume command:

```sh
claude -p --resume <session-id> --output-format json "<continuation message>"
```

- `-p` (print mode) because the process is not attached to a terminal: ccresu never sends keystrokes and never allocates a pty.
- `--resume <session-id>` so the original conversation continues instead of a new one starting.
- The continuation message defaults to a request to continue the existing active goal, and can be overridden per session.
- The command runs in the session's recorded working directory, so relative paths and project configuration still apply.

## Why the message is the last argument

The prompt is a positional argument: no flag introduces it. Position is the only thing that says which invocation it belongs to, and the documented form is `claude -p --resume <session-id> <prompt>`, so the message follows the session it is said to. ccresu keeps it last, after both flags, and builds the vector in one place.

internal/claude/cli.go:

```sh
func ResumeArgs(sessionID, message string) []string {
	return []string{"-p", "--resume", sessionID, "--output-format", "json", message}
}
```

- `TestResumeArgsExact` asserts the joined vector, so a reordering is a failing test rather than a puzzling runtime refusal.
- `Resume` hands the same slice to the first attempt and to the repeat after `claude stop`, so the second invocation cannot be a subtly different command.
- The attempt's `command` column, rendered by `commandPreview`, prints the same order: `claude -p --resume <session-id> --output-format json <N-byte continuation message>`, with the placeholder where the message really sits.
- Only a summary is stored, never the text: the column says how many bytes were sent, and the conversation stays in the transcript.

> **Note: Why the audit trail has to match**
>
> `ccresu history` is an audit trail. The preview used to print the flags after the `<message>` placeholder, describing an invocation ccresu never ran — worse than no preview, because it looks authoritative. It now renders exactly the order `claude.ResumeArgs` executes.

## When a background agent still holds the session

`claude -p --resume` refuses outright while the same session is attached to the interactive CLI's background agent: the CLI answers `That session is running in the background (837eaaea). Run claude attach 837eaaea to open it, or claude stop 837eaaea first to resume it here. Add --fork-session to branch off a copy instead.` Nothing about the conversation is lost there, so it must not end the session's life.

1. The refusal is recognised after normalisation — ANSI colour codes stripped, indentation and line wrapping collapsed — so a restyled message still matches, and an unrelated failure is not mistaken for this one.
2. `claude stop <job-id>` releases the background agent. The job name is the eight lower-case hex name this very refusal prints (`837eaaea`), never the session UUID: `claude stop` resolves job names only and answers a UUID with `No job matching` and exit 1. A refusal that names no job is not stopped at all — guessing could stop another session's agent. The stop is written to the log, never to the attempt row: `ccresu history` still shows the one resume command that was run.
3. The identical resume is issued once more — same arguments, same session id, same continuation message — and its result becomes the attempt's result. It is not a second try against the budget: the attempt keeps its number.

| Step | What the CLI sees | What ccresu records |
| --- | --- | --- |
| 1 | `claude -p --resume <id> --output-format json "<message>"` — refused, the session is in the background | the attempt, with its single resume command as `command` |
| 2 | `claude stop <job-id>` — eight hex characters, never the session UUID | a log line only: the attempt row still shows one resume |
| 3 | the same resume, byte-identical arguments | the attempt's result, verification included |

**Figure: One attempt, three calls**

The resume is refused because the session is still attached to the background agent. ccresu runs `claude stop <job-id>`, then issues the identical resume with the same arguments, inside the same attempt. That second result becomes the attempt's result, and RESUMED is written only after verification.

(An SVG diagram on the page; it is not reproduced in text. See https://jymchng.github.io/ccresu/docs/.)

> **Warning: Stopped once, and only once**
>
> If the stop itself fails, or the second resume refuses again (or fails any other way), the original error is returned untouched: nothing loops and the classification is unchanged. `--fork-session` is still never used — it would continue a copy of the conversation — and `claude attach` needs a terminal ccresu does not have, which is exactly why `stop` is the one remedy taken. A session stopped this way resumes normally next time, because the background agent no longer holds it.

## The operator exit from DISCOVERED

A session that ended `DISCOVERED` this way — or any other way — is not lost. `ccresu retry <session-id>` is how an operator says so, and it is deliberately narrow.

- It moves `DISCOVERED` to `DISABLED` and nothing else: any other state is refused with exit code `4` and a message that names the state and the command to use instead.
- It clears the stored error, so the session no longer looks broken.
- It keeps the attempt row, its reason and the counter, so `ccresu history` still explains what happened.
- It never resumes anything and never refunds an attempt. `ccresu retry <id>` refills the budget, `ccresu recover <id> --force` tries once more now, and `ccresu enable <id>` makes the session recoverable again with whatever budget it has left.

## Proving it end to end

This is not only asserted against fakes. `make e2e` runs `tests/scripts/background-resume-e2e.sh`, which builds the real binary and puts a stub `claude` on `PATH`. The stub keeps a background-agent marker, refuses the first `-p --resume` with the CLI's text above, clears the marker on `claude stop <job-id>`, and then returns a JSON result with the same `session_id` after growing the transcript. The stub resolves its argument the way the real CLI does — only an eight-hex job name it holds, anything else answered with `No job matching` and exit 1 — so a stop that carried the session UUID fails there exactly as it does in the field. The run asserts that `ccresu recover <id>` exits 0 and ends `RESUMED` with the verification “proven: session id preserved and transcript grew”, that the stub saw exactly resume, stop, resume with byte-identical resume arguments, and that `ccresu history` still records the single resume command. One more assertion closes the gap the field found: the stop carried the job name and never the session UUID.

The contrast, against the pre-fix commit:


## Verification

A process starting proves nothing: Claude Code may exit immediately, or may create a new conversation. After the resume, the verifier waits up to `recovery.verification_timeout` for two facts:

1. The session id still exists in discovery and is the same id that was interrupted.
2. The transcript for that id grew: the conversation continued instead of being recreated.

> **Note: Why both checks**
>
> The id proves the conversation was resumed rather than forked; the transcript growth proves the resume actually produced work. Only then is RESUMED written and the success notification sent.

## Waiting for the reset

The reset time is parsed out of the limit message itself. `resets 12pm (Europe/Berlin)` becomes noon in Berlin, stored as a UTC instant with the original timezone kept for display, and the wait is unaffected by the host timezone or by a DST change in between. When the message carries no reset time, ccresu polls with exponential backoff starting at `scheduler.unknown_reset_initial_interval` (5m) up to `unknown_reset_max_interval` (30m).

## Restarts and duplicate prevention

- Sessions, schedules and attempts are persisted, so a restart or reboot resumes waiting with the original deadline.
- One recovery loop per session is enforced by a per-session lock, so two triggers cannot resume the same session twice.
- Transitions are idempotent: re-observing a state that is already recorded does not add a duplicate row.
- A crash mid-attempt leaves a stale attempt that the next pass reconciles before starting a new one.

## Observing a recovery

Follow one session:

```sh
ccresu inspect <session-id>        # state, schedule, attempts
ccresu history <session-id>        # every recorded transition
curl -N http://127.0.0.1:8787/api/v1/events   # live SSE feed
```
